Invisible Clicks

クリックジャッキングを体験・理解するための教育用デモです

クリックジャッキングとは？

クリックジャッキング（Clickjacking）は、Webサイトのユーザーインターフェースを悪用する攻撃手法です。

🎭 攻撃の仕組み

攻撃者は透明または不透明なレイヤーを使用して、ユーザーが意図しない操作を実行させます。

  • 透明なiframeやボタンを重ねる
  • 見た目は無害なボタンの上に、透明なクリック対象を配置
  • ユーザーのクリックを意図しない操作に誘導

⚠️ 想定される被害

埋め込みが許可され、必要な認証や操作条件を満たしている場合の例です。すべてのサイトで成立するわけではありません。

  • SNSの「いいね」や「フォロー」を無断で実行
  • 金銭的な取引の承認
  • 個人情報の削除や変更

ブラウザーやOSの権限確認画面はページ内のボタンとは別です。透明なHTML要素を重ねるだけで、カメラやマイクを無条件に許可できるとは限りません。本ツールは権限を要求せず、カメラやマイクを使いません。

📊 攻撃の種類

  • 古典的クリックジャッキング（Classic Clickjacking）：透明なiframeを使用
  • ライクジャッキング（Likejacking）：SNSの「いいね」ボタンを悪用
  • カーソルジャッキング（Cursorjacking）：見かけのカーソル位置と操作位置をずらす
  • ファイル操作への誘導：見かけと実際のドロップ先などをずらす

💡 デモの使い方

  1. 「偽UI」の「👍 いいね！」をクリックまたはタップしてください。
  2. 透明オーバーレイでは、上に重ねた透明ボタンがクリックを受け取り、300ms後に削除を模したログを表示します。
  3. ラジオボタンで方式を切り替えてください。「攻撃を無効化」は偽UIを隠し、正規UIだけを残します。

これは同じページ内の要素による模式デモです。実際のiframe、外部サイト、秘密情報の削除は使わず、防御ヘッダーの有効性も検証しません。正規UIは比較用に常時表示します。

透明ボタンはポインター操作専用です。どちらの方式でも、Tabキーで「いいね！」に移動してEnterまたはSpaceで操作すると、通常の「いいね」のログを表示します。これはキーボード操作一般の安全性を保証するものではありません。

方式変更、タブ移動、「ログを消す」で、まだ表示されていない結果を取り消します。実際のサイトで成立済みの操作を取り消す機能ではありません。

クリックジャッキング攻撃の理論

🔬 技術的メカニズム

クリックジャッキングは、見えている操作と実際にクリックを受ける対象の食い違いを利用します。

1. Z-Indexとレイヤー構造

クリックジャッキングの基本原理です。CSSのZ-Indexを使って、ユーザーが見える「偽のボタン」の上に、透明な「危険なボタン」を重ねます。ユーザーがクリックすると、実際には上層の危険なボタンが反応します。

/* 攻撃者のページ */
.attack-container {
  position: relative;
  width: 500px;
  height: 300px;
}

.fake-play-button {
  position: absolute;
  z-index: 1;  /* 下層 */
  background: #28a745;
  color: white;
  padding: 10px 20px;
}

.invisible-iframe {
  position: absolute;
  z-index: 2;  /* 上層 */
  opacity: 0;  /* 完全に透明 */
  width: 100%;
  height: 100%;
}

ユーザーには「無害なボタン」が見えますが、実際のクリックは透明なiframe内の別のボタンを押すことになります。

2. 透明度とポインターイベント

opacity: 0は要素全体を透明にしますが、それだけではポインター操作を止めません。背景色だけの透明化は文字や子要素を消さないため、同じ効果ではありません。pointer-events: noneはポインターの対象から外す指定であり、キーボードのフォーカスを無効にする指定ではありません。

/* 要素全体を透明にしてもクリックを受け付ける */
.clickable-invisible {
  opacity: 0;
  pointer-events: auto;  /* クリックを受け付ける */
}

.visible-but-not-clickable {
  opacity: 1;
  pointer-events: none;  /* ポインターのクリック対象から外す */
}

3. iframeの悪用パターン

見かけのボタンの上に透明なiframeを重ね、iframe内の操作対象と位置を合わせる模式例です。対象サイトが埋め込みを許可し、必要な認証などの条件も満たす場合に成立し得ます。以下は表示専用のコードで、このページではiframeを作成しません。

<!-- 表示専用の模式例。example.invalidは例示用の予約ドメイン -->
<div class="attack-container">
  <!-- 下層：見かけのコンテンツ -->
  <button class="fake-play-button">
    🎬 無料動画を再生
  </button>
  <!-- 上層：透明なクリック対象。配置は外部CSSで指定 -->
  <iframe class="invisible-iframe"
    src="https://example.invalid/account"
    title="透明なiframeの模式例">
  </iframe>
</div>
🎭 高度な攻撃テクニック

1. 2段階操作の概念例

同じボタンを2回押すと処理が変わる、単純な概念例です。 別ウィンドウを閉じてクリック先を切り替えるDoubleClickjackingの再現ではありません。 そちらの手法と防御上の違いは OWASPの説明 を参照してください。 

let clickCount = 0;
document.querySelector('.target').addEventListener('click', () => {
  clickCount++;
  if (clickCount === 1) {
    // 1回目: 偽のアクション
    showFakeAction();
  } else if (clickCount === 2) {
    // 2回目: 別の模擬処理へ切り替える
    showSecondSimulatedAction();
  }
});

2. ドラッグ&ドロップジャッキング

見かけのドロップ先と実際の受け取り先をずらす概念です。iframeを置くだけで任意のファイルが転送されるわけではなく、ドロップ先の実装、ブラウザーの制約、利用者の操作に依存します。本ツールにはファイルの受け取りや送信機能はありません。

<!-- 下層：見かけのドロップエリア -->
<div class="fake-drop-zone">
  ここに画像をドロップ
</div>

<!-- 上層の候補を表すだけの模式例。URLを読み込まない -->
<iframe class="invisible-iframe"
        src="https://example.invalid/drop"
        title="ドロップ先の模式例">
</iframe>

3. タイミング攻撃

クリック前に重なりや位置を変える概念例です。実際に別の対象へ届くかは、挿入位置と操作のタイミングによります。このコードは表示専用で実行しません。

// ホバー時に瞬間的にiframeを挿入
button.addEventListener('mouseenter', () => {
  setTimeout(() => {
    insertMaliciousIframe();
  }, 100);  // 100ms後に挿入
});

// 元のbuttonのclickハンドラーで、別iframeへのクリックを
// 観測できるわけではありません。
🌍 想定シナリオと成立条件

以下は仕組みを考えるための想定例であり、特定のサービスで発生した事件や被害件数の報告ではありません。

📦 SNS操作への誘導

見かけの再生ボタンに、SNSの操作対象を重ねる想定です。

  • 見かけのコンテンツの上に透明な「いいね」の操作対象を配置
  • 埋め込みが許可され、必要なログイン状態が利用できることが条件
  • 防御は対象ページの埋め込み制限を中心に検討

💳 重要操作への誘導

ゲームの操作に見せかけ、設定変更などの承認を押させる想定です。

  • 対象画面を埋め込めることに加え、処理に必要な認証・入力・確認の条件が必要
  • 一度クリックしただけで、どのサイトでも送金が成立するわけではない
  • 埋め込み制限と、操作内容を結び付けた再認証やサーバー側の認可を併用

📱 カメラ・マイク権限との違い

HTMLの重ね合わせと、ブラウザーやOSが表示する権限確認は区別します。カメラやマイクの利用には、安全なコンテキスト、利用者の許可、iframeのPermissions Policyなどの条件があります。WebViewでもOS・アプリ・実装によって条件が異なります。

このデモから実機の権限詐取の成否は判断できません。詳しくはMDNのgetUserMediaの制約を参照してください。

🔍 埋め込み状態の確認と限界

JavaScriptによる状態確認（表示専用サンプル）

// iframe内かどうかだけを確認する。悪意は判定できない。
const isEmbedded = window.self !== window.top;
if (isEmbedded) {
  console.info('このページはフレーム内で表示されています');
}

正当な埋め込みでも同じ結果になります。また、クロスオリジンの親ページのDOMや位置・透明度を自由に読むことはできません。透明要素の走査にも誤検出や見落としがあるため、攻撃の証明や安全性の判定には使えません。

🛠️ セキュリティツールでの検査

  • ブラウザーの開発者ツール：Elementsで要素の重なり、NetworkでHTTPレスポンスヘッダーを確認
  • ヘッダーがあるかだけでなく、設定値と実際の埋め込み可否を確認
  • スキャナーの警告は調査の手掛かりであり、攻撃の成立を単独で証明するものではない
  • 外部の検査サービスにはURLなどを送信するため、所有者の許可と情報の扱いを確認

クリックジャッキング対策

🔒 HTTPヘッダーによる対策

保護対象のページのHTTPレスポンスヘッダーで、どの親ページから埋め込めるかを制限します。以下は別々の設定候補です。サービスの埋め込み方針に合うものを選びます。

frame-ancestorsとX-Frame-OptionsはHTTPレスポンスヘッダー専用です。 HTMLのmetaに書いても効きません。 本ツールのmeta CSPは読込元を制限するもので、他サイトからの埋め込みを拒否する設定ではありません。 MDN：frame-ancestors

1. X-Frame-Options（従来の方法）

# すべてのドメインからのiframe埋め込みを拒否
X-Frame-Options: DENY

# 同一オリジンからのみ許可
X-Frame-Options: SAMEORIGIN
DENYはすべての埋め込みを拒否し、SAMEORIGINは同一オリジンに限定します。 廃止されたALLOW-FROMは現在のブラウザーで無視されるため使用しません。 MDN：X-Frame-Options

2. Content-Security-Policy: frame-ancestors（推奨）

# すべてのドメインからのiframe埋め込みを拒否
Content-Security-Policy: frame-ancestors 'none';

# 同一オリジンからのみ許可
Content-Security-Policy: frame-ancestors 'self';

# 複数のドメインを指定
Content-Security-Policy: frame-ancestors 'self' https://first.example.invalid https://second.example.invalid;

# サブドメインを許可（example.invalid自体は含まない）
Content-Security-Policy: frame-ancestors 'self' https://*.example.invalid;
frame-ancestorsは「自分を埋め込む親」を制限します。自分が読み込むiframeを制限するframe-srcとは別です。default-srcからも継承されないため、埋め込み方針を明示します。

実装例（Node.js Express）

// すべての埋め込みを拒否する、両ヘッダーで整合した方針
// ルートの登録より前に適用する
app.use((req, res, next) => {
  res.setHeader('X-Frame-Options', 'DENY');
  res.setHeader('Content-Security-Policy', "frame-ancestors 'none'");
  next();
});

frame-ancestorsを含む強制用CSPに対応するブラウザーでは、その指定がX-Frame-Optionsより優先されます。方針を食い違わせず、配信されるヘッダーと埋め込み結果を確認してください。

設定例は埋め込み制限の部分だけです。既存CSPをこの断片で置き換えず、script-srcなどの必要な設定を保ってframe-ancestorsを統合してください。

⚡ アプリケーション側の対策

埋め込み制限を基本とし、操作内容の確認や認証を補助として組み合わせます。個々の対策だけで、すべてのクリック誘導を防げるわけではありません。

1. 重要操作の再認証

削除、送金、設定変更などでは、操作内容を明示した再認証を検討します。認証結果を対象の操作に結び付け、サーバー側の認可も確認します。単に確認ボタンを増やすだけでは、そのボタン自体を誘導される可能性が残ります。

2. CSRF対策とクリックジャッキング対策の区別

<!-- HTMLフォーム例（送金や設定変更など重要な操作） -->
<form method="POST" action="/transfer">
  <input type="hidden" name="csrf_token" value="{{ csrf_token }}">
  <input type="text" name="recipient" placeholder="送金先">
  <input type="number" name="amount" placeholder="金額">
  <button type="submit">送金する</button>
</form>

// サーバー側の概念例。各ミドルウェアは別途用意する。
// csrfProtectionは、欠けた・不正なトークンを拒否する
// フレームワークの機能を使用する。認証・入力・認可は別に検証する。
app.post('/transfer',
  requireLogin, csrfProtection, validateTransfer, authorizeTransfer,
  (req, res) => {
    processTransfer(req.body);
  }
);

CSRFトークンは別種の攻撃であるCSRFへの対策です。 埋め込まれた正規ページのフォームを押すクリックジャッキングでは、有効なトークンもそのまま送信され得ます。 トークンだけではこの操作誘導を防げません。 このコードは概念例であり、実運用ではフレームワークのCSRF対策を利用してください。 PortSwigger：CSRFとの違い

3. Frame Busting（補助的対策）

JavaScriptでフレーム内かを調べ、トップレベルへ移動しようとする補助策です。sandbox、トップレベルへのナビゲーション制限、JavaScriptの無効化などによって、期待通り動作しない場合があります。HTTPヘッダーによる埋め込み制限の代わりにはしません。

4. 強調表示と確認ダイアログの限界

iframe内のボタンのz-indexを大きくしても、親ページがiframe全体に設定した透明度や重なりから抜け出せません。強調表示や自作モーダルは操作のわかりやすさには役立ちますが、埋め込み防御にはなりません。

ブラウザーのconfirmなども万能ではなく、sandboxやブラウザーの制限で表示されない場合があります。 確認を実施するなら「表示されなかった場合も処理を進めない」設計が必要です。 HTML仕様：単純なダイアログ

5. SameSite Cookieの役割

SameSite=LaxまたはStrictは、クロスサイトiframeなどへの認証Cookie送信を制限する補助策です。 埋め込み自体を禁止せず、認証不要の操作や、同一サイトに属する別オリジンまで一律に保護するものではありません。 OWASP：SameSite Cookie

🎯 実装のベストプラクティス

セキュリティは多層防御が重要です。以下の対策を組み合わせて実装しましょう。

📋 実装チェックリスト

位置づけ 対策 役割 注意点
基本 CSP frame-ancestorsヘッダーの設定 埋め込み元を制限 HTTPヘッダー専用

⚙️ 設定例（Apache）

# .htaccessファイル
Header always set X-Frame-Options "SAMEORIGIN"
Header always set Content-Security-Policy "frame-ancestors 'self'"

⚙️ 設定例（Nginx）

# nginx.conf
add_header X-Frame-Options "SAMEORIGIN" always;
add_header Content-Security-Policy "frame-ancestors 'self'" always;

🔍 テスト方法

  1. 所有または検査許可のあるサイトで、開発者ツールのNetworkからレスポンスヘッダーを確認
  2. 許可する親と許可しない親から埋め込みを試し、実際のブラウザーで確認
  3. ログイン状態、Cookieの条件、必要な操作まで含めて結果を評価
  4. 本ツールの模式デモでは上記の防御検証はできないため、管理下の別環境を使用
